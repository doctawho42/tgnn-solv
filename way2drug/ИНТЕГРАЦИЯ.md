## 2. Требования к серверу

| ресурс | сколько нужно | измерено |

примерно 2 ГБ.

## 3. Установка

```bash
tar xzf way2drug_solubility_v1.0.tar.gz
cd way2drug_solubility_v1.0
python -m venv venv && . venv/bin/activate
pip install -r requirements.txt
```

Затем в окружении процесса, который будет считать:

```bash
export PYTHONPATH=/путь/к/way2drug_solubility_v1.0
export W2D_CHECKPOINT_DIR=/путь/к/way2drug_solubility_v1.0/checkpoints
export KMP_DUPLICATE_LIB_OK=TRUE
```

Последняя переменная обязательна и не косметическая: rdkit, torch и scikit-learn каждый
несут свою копию libomp, и при импорте двух из них процесс аварийно завершается с
`OMP: Error #15`. Без этой переменной сервис упадёт на старте.

### Проверить, что всё встало

```bash
python -m pytest tests -q                 # ожидается: 14 passed
python -m w2d_solubility.cli "CC(=O)Nc1ccc(O)cc1"
```

Если тесты прошли, а CLI выдал таблицу с DMF наверху — установка корректна.

## 4. Как подключать: три схемы

### Схема А. Внутри процесса — если backend на Python

Лучший вариант: модель живёт в памяти рабочего процесса, накладных расходов нет.

```python
from w2d_solubility import SolubilityPredictor

PREDICTOR = SolubilityPredictor()          # ОДИН раз при старте процесса, не на запрос

def handle(smiles: str, temperature: float | None = None) -> dict:
    return PREDICTOR.predict_panel(smiles, temperature=temperature)
```

Предиктор создаётся один раз на процесс. Разделяемого изменяемого состояния у него нет:
модели, панель и ассеты только читаются, таблица под каждый запрос строится своя.

### Схема Б. Отдельный микросервис — если backend не на Python

Поднимаете сервис рядом и ходите в него по HTTP. Это рекомендуемый путь, если платформа
на PHP.

```bash
python -m w2d_solubility.service --host 127.0.0.1 --port 8080
```

Слушать надо **только на 127.0.0.1** и проксировать через ваш веб-сервер: встроенный
`http.server` не рассчитан на публичную нагрузку и не имеет ни ограничения частоты
запросов, ни защиты от медленных клиентов.

Для боевой нагрузки лучше завернуть предиктор в gunicorn/uvicorn с несколькими воркерами,
чем масштабировать `service.py`. Он в комплекте как демонстрация формата ответа.

### Схема В. Вызов CLI — работает, но осторожно

```bash
python -m w2d_solubility.cli --json "CC(=O)Nc1ccc(O)cc1"
```

**Тут закопана ловушка.** Импорт torch и rdkit стоит **5,2 секунды и 382 МБ** — до того,
как начнётся хоть какой-то счёт. Запуск CLI на каждый пользовательский запрос означает
5,5 секунды ожидания вместо 0,2 и полгигабайта на каждый параллельный вызов. Так делать
можно только для пакетной обработки файла, где эти 5 секунд платятся один раз на тысячу
структур.

Для интерактивной страницы используйте схему А или Б.

## 5. Производительность и кэш

| | |
|---|---|
| холодный старт процесса | **≈ 5,5 с** (5,2 импорт + 0,2 загрузка весов) |
| один запрос, установившийся режим | **0,19 с** (худший из замеров 0,23 с) |
| пропускная способность | **≈ 5 структур/с** на один процесс |

Холодный старт платится один раз за жизнь процесса. Поднимайте воркеры заранее, не по
первому запросу.

**Ответ детерминирован**: одна и та же структура при одной и той же температуре всегда даёт
одни и те же числа. Значит, результат можно кэшировать, и ключом должен быть
**канонический** SMILES из поля `canonical_smiles`, а не то, что ввёл пользователь: `OCC` и
`CCO` — одна и та же молекула, и без канонизации кэш будет промахиваться на ровном месте.

```
ключ кэша = canonical_smiles + ":" + temperature_K
```

Панель из 27 растворителей считается за один проход, поэтому запрашивать её целиком дешевле,
чем дёргать по растворителю.

## 6. Обработка пользовательского ввода

Нераспознанная структура **не является сбоем сервиса**. Ответ приходит с полем `error`, и
показывать надо именно его текст:

```json
{"input": "не структура", "error": "RDKit не смог разобрать структуру"}
```

Пакетный прогон при этом не прерывается: остальные структуры считаются как обычно.

Что стоит проверить на своей стороне до вызова:

- пустая строка — отсекать сразу;
- очень длинный ввод — разумно ограничить длину строки SMILES (тысячи символов означают
  полимер, который всё равно будет отвергнут по размеру);
- партия — не больше 50 структур за запрос в схеме Б (это ограничение зашито в `service.py`
  и вернёт HTTP 413).

## 7. Что показывать на странице

Порядок по важности, если места мало:

1. **Ранжированный список растворителей.** Это ответ на вопрос, ради которого приходят: не
   «сколько граммов», а «в каком растворителе лучше».
2. **Флаг применимости `in_domain` и заметки `notes`.** Число вне области применимости хуже,
   чем отсутствие числа. Заметки написаны так, чтобы их можно было показывать пользователю
   дословно.
3. **Интервал `ln_x2_interval`**, а не только точечное значение.
4. **Концентрация в г/л** — самое понятное для практика число, но выдаётся не всегда;
   когда её нет, причина лежит в `concentration_note` и её тоже стоит показать.

Три вещи, которые желательно не потерять в вёрстке:

- Пометку **«вещество присутствует в обучающей выборке»**. Без неё пользователь примет
  предсказание за независимую проверку точности.
- Оговорку, что модель **не учитывает pH, полиморфизм, соли и смеси растворителей** — она
  предсказывает одно число по структуре. Полный список в MODEL_CARD.
- Порядок величины ошибки. Типичное предсказание расходится с истиной примерно **в пять
  раз**; при этом сами лабораторные измерения одного вещества расходятся в 2–5 раз. Второе
  число объясняет первое, и без него сервис выглядит хуже, чем он есть.

## 8. Эксплуатация

**Логи.** `service.py` пишет обращения в stderr. Трассировки внутренних ошибок в ответ
пользователю не уходят — только `{"error": "внутренняя ошибка предсказания"}`, — но в логе
они есть.

**Что мониторить.** Память процесса (должна стоять около 520 МБ и не расти) и время ответа
(медиана 0,19 с; заметный рост означает, что процессов меньше, чем нужно нагрузке).

**Обновление модели.** Если однажды приедут новые веса, порядок такой:

```bash
python verify_against_checkpoint.py     # требует тестовой выборки проекта, запускать у нас
python -m pytest tests -q
```

Первая проверка — главная. Сервис строит признаки не копией обучающего кода, а самим
обучающим кодом, и ошибка в этой сборке даёт **работающий** сервис с тихо другими числами.
Единственный способ это увидеть — сравнить MAE с записанной в чекпойнтах. На версии 1.0
расхождение 0,0000 на всех трёх сидах.

## 10. Вопросы, которые стоит решить до запуска

Это не технические блокеры, а решения, которые я не могу принять за вас.

1. **Панель из 27 растворителей** — все с опорой не менее 100 разных веществ в обучении.
   Если для интерфейса это много, разумно показывать первые 10, оставив полный список
   по кнопке. Урезать саму панель не нужно: считается она за один проход.
2. **Порог области применимости 0,40 по Танимото** не калиброван под точность — это грубый
   фильтр «модель такого не видела», а не измеренная граница ошибки. При желании его можно
   откалибровать по тестовой выборке; сейчас он намеренно назван порогом предупреждения.
3. **Температура.** Сейчас по умолчанию 25 °C и поле для ввода. Если поле в интерфейсе не
   нужно, его можно убрать — сервис ответит на 298,15 K.
